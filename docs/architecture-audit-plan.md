# 架构可用性、可读性与可维护性审计方向

本文定义后续审计范围、顺序与验收标准，不是已经完成的代码审计，也不将待核查事项认定为现存缺陷。依据是当前工程边界与近期配置、诊断、GUI 和两板适配过程中暴露的问题类型。

目标是让开发者能完成“克隆工程、选择开发板、配置功能、编译调试、增加应用”这条完整路径，并能准确判断问题发生在哪一层。遵循少层级、少重复规则的原则，不以宏数量、文件长度或新增抽象数量作为重构成绩。

## 1. 审计优先级

| 优先级 | 方向 | 需要回答的问题 | 预期产物 |
| --- | --- | --- | --- |
| P0 | 可复现的两板工作流 | 新环境是否能按文档完成两板构建，是否依赖本地缓存和未提交源码？ | 克隆到构建的步骤及依赖清单 |
| P0 | 配置到运行的完整链路 | JSON 中启用的功能是否真正编译、初始化并运行？关闭后是否完整退出？ | 功能选择与实际行为对照表 |
| P0 | 诊断结果可信度 | started、passed、ready、count 分别证明什么，快照是否可能停更？ | 诊断状态定义与观测方法 |
| P1 | 硬件与应用边界 | 固定引脚、应用别名、设备选择和算法参数是否各有唯一归属？ | 字段归属表及越界候选清单 |
| P1 | 启动与调度 | 应用应在哪里加入，初始化顺序和线程负载是否清楚？ | 启动链和线程资源表 |
| P1 | CMake 与生成器 | 修改一个功能需同步多少处，源码选择和生成声明是否一致？ | 构建职责图及重复规则清单 |
| P1 | GUI 与固件一致性 | GUI 允许的配置能否被生成器接受，恢复默认是否和真实缺省一致？ | 跨层配置用例与结果 |
| P2 | API、宏与文档 | 接口的适用范围是否清楚，条件编译是否隐藏了空实现或缺失符号？ | 小范围整理建议及文档修正清单 |

## 2. 两板切换和仓库交付（P0）

近期 worktree 路径问题说明，已有工作区能构建，并不意味着新克隆可以复现。优先沿真实使用流程审查，而不是只读 CMake。

检查方向：

- 父仓库和各子模块的提交是否组成可复现版本；F4 分支的获得方式是否明确。
- 区分 PNX_BOARD 的板型选择与 BSP 分支切换：工具是否暗示它能自动完成实际上没有完成的动作。
- 普通构建、开发覆盖参数和回归矩阵是否明确区分，是否残留本地 worktree、绝对路径或缓存依赖。
- 切换板型、切换 Debug/Release、重配已有目录和全新配置的行为是否一致。
- launch/tasks 的 ELF、OpenOCD target 和构建 preset 是否始终对应同一板型。
- 同级 GUI 工程的开发依赖与安装后运行依赖是否区分；共享默认数据更新后是否需要重新打包，以及文档是否说明。

验收：从干净构建目录、已记录的源码版本出发，按文档分别完成 H7/F4 构建；板型与 BSP 不匹配时错误能明确指向处理方法，不依赖历史 CMakeCache。不要通过自动切 Git 分支掩盖交付布局问题。

## 3. 配置语义与功能闭环（P0）

近期出现过关闭模块仍需参数、测试 binding 自动进入默认值、GPIO 测试固定 LED 等问题。审计重点是一个字段从填写到执行是否闭环。

对 USBX、遥控器、referee、BMI088、AHRS、DMIMU、电机、LED、UART/CAN/GPIO 测试逐项追踪：

```text
用户 JSON → 默认值合并 → 资源解析 → 生成常量/绑定
          → CMake 源码选择 → 启动调用 → 可观测运行结果
```

检查方向：

- 区分字段缺失、显式 false、none、空对象、无效值，避免不同入口自行定义缺省行为。
- 确认 common、板型默认值、用户覆盖按字段合并；只填写一个参数时，其余常量仍完整。
- 关闭模块不要求无关参数；重新开启时已有配置可以继续使用，不应由 GUI 悄悄删除。
- 推荐值、默认值、实际 binding 必须区分，推荐一个串口不代表自动启用消费者。
- test 选择与产品模块选择分离；启用 test 不应成为业务模块的唯一构建入口。
- 兼容旧字段是否有明确策略，例如 gpio_leds 已变为单输出测试，命名是否持续误导用户。
- 任意扩展 JSON 字段被保留，不等于已取得固件语义；拼错内置字段时，用户是否容易误以为已经生效。

验收：每个功能都能说明启用字段、所需 binding、生成符号、源文件和启动入口；至少覆盖关闭、开启、部分参数和缺少依赖四类输入。验证聚焦已有功能，不新增通用配置语言。

## 4. 诊断可用性与状态含义（P0）

近期的 started=false、订阅失败、温度 ready 但无解算、计数冻结等现象，要求把“初始化成功”“线程运行”“数据更新”“测试通过”分开解释。

检查方向：

- started 是否代表请求已提交、初始化完成还是线程已经执行；启动中途失败后状态是否自洽。
- passed 是初始化检查结果、当前状态还是累计结论；成功返回 HAL 调用不能描述成物理引脚或总线已验证。
- observed_count、update_count、gyro_ready_count 等计数的生产者、更新条件和快照刷新频率是否明确。
- 监控线程被饿死时，是否有直接读取实际服务状态的方法；避免再引入一套复杂遥测体系。
- UART 主机超时能否区分未打开端口与已打开但没有响应；协议长度、波特率、绑定和固件选择是否容易核对。
- USB 枚举、CDC 连接、收发验证是否分开；仅链接通过不应记为 USB 测试通过。
- GPIO 当前是输出翻转，不是引脚测量或输入测试；GUI 和文档是否准确表达范围。
- 测试与产品消费者选择同一资源时，是否可能互相覆盖回调或改变状态；先确认现有冲突检查是否足够，不追加资源管理框架。

验收：每个诊断状态有简短定义，用户可根据少量字段确定下一步定位方向。硬件通过与软件构建通过分别记录。

## 5. Board、Device、Module、Application 边界（P1）

检查方向：

- IOC 是否独占引脚复用、时钟、DMA、NVIC、定时器等外设配置；board.json 是否只补充固定连接和静态事实。
- params 中的 GPIO/UART/CAN 等别名是否只是选择已有资源，没有复制硬件配置。
- robot 是否负责选择消费者和设备组成，板级固定设备是否没有混入启用开关。
- 业务应用是否只依赖公共 BSP 与生成名字，没有引用 HAL handle 或 BSP 私有头文件。
- F4/H7 的真实差异是否留在实现侧；共同语义是否真的一致，而非仅函数签名相同。
- H7 SPI LED 与 F4 GPIO 灯是否清楚说明支持范围，不把空实现当作跨板支持。
- 模块是否把具体开发板资源选择写死；同一个模块换一组合法 binding 能否使用。

验收：每类配置只有一个权威归属；必要 MCU 差异能够明确列出，不以新增虚接口、工厂或运行时板型选择解决编译期问题。

## 6. 启动、线程与性能边界（P1）

检查方向：

- Core 的 ThreadX 入口、app_start、diagnose_start、设备初始化和服务启动顺序是否容易追踪。
- 用户新增业务应用是否只需修改应用目录，是否误把 diagnose 当成应用框架。
- 初始化阶段调用的订阅、锁和等待操作是否适合当时的 ThreadX 上下文。
- AHRS 采样、校准、温控、解算和发布之间的前置条件是否清楚，是否存在低优先级线程无法更新导致的表象误判。
- 区分线程目标周期、DRDY 频率、实际处理耗时与有效发布频率；1 ms 周期不应表述为 MCU 主频。
- SPI 阻塞读取耗时占用的是哪个线程、哪条总线，是否实际影响其他消费者；不能仅凭 77 μs 就决定改 DMA。
- 临时 DWT 测量字段是否已完成使命，移除范围和时机是否明确。

验收：形成紧凑的线程表，包含启动者、优先级、等待条件、栈来源与发布频率；性能建议必须对应测量或可复现现象，避免先增加异步状态机。

## 7. CMake、生成器与条件编译（P1）

检查方向：

- CMake 对完整模块的源文件裁剪是否与生成声明、头文件可见性和调用入口一致。
- HAS_*、ENABLE_* 是否分别表示硬件事实、消费者选择或实现选择；同义变量是否可收敛。
- #if 是否保护真正不存在的类型、头文件或绑定；不要将普通逻辑全部改成宏，也不要机械替换为 if constexpr。
- 多处空函数是否掩盖模块关闭；整文件选择是否能替代分散条件编译。
- 默认值、枚举、依赖规则是否在 Schema、生成器、GUI 和源码中重复维护。
- 新增一个 binding 或模块参数的修改面是否可预测；生成器内部变量依赖是否隐蔽。
- CubeMX 再生成后，USER CODE、USBX 适配和构建集成是否仍可保留；只读检查生成所有权，不手改 HAL 文件模拟硬件资源。

验收：优先在已有文件中合并重复职责。只有完整职责确实独立且降低维护成本时才拆文件，不以缩短行数为目标。

## 8. GUI 工作流与固件一致性（P1）

检查方向：

- Application/Robot 跳转是否保持板型、未保存修改和正确编辑器类型。
- 修改字段、添加 binding、折叠模块后，滚动位置、焦点和搜索状态是否稳定。
- 硬件资源选择是否来自当前板型；过期导出是否被误用为当前资源。
- 默认值快照与固件 defaults.json 是否来自同一版本，恢复默认是否与缺省构建一致。
- PS2 等条件参数是否仅在所属功能选中时参与检查；本地问题提示是否与 CMake 一致。
- 关闭测试后保留 binding，重新打开可继续使用；缺少 binding 的提示是否能直接完成配置。
- 检查导出器、模型测试和真实 VS Code 操作的覆盖边界，不能把模型测试通过描述成完整 GUI 交互已验证。

验收：围绕用户完成任务的路径测试，不只验证单个表单控件。固件不能依赖编辑器缓存才能构建。

## 9. 文档与回归资产（P2）

- 整理 AGENTS、配置文档和 diagnose README 中相互矛盾或已过期的状态；历史证据保留日期和适用提交。
- 每个 test 字段说明真实能力、依赖和观察字段；明确尚未实现的 ADC、独立 SPI/PWM/EXTI 专项测试。
- 矩阵脚本记录当前真正覆盖的用例，不继续引用旧脚本曾覆盖而新脚本没有覆盖的组合。
- 保留能验证跨层行为的回归，删除只复述实现的低价值检查。
- 构建日志和 ELF 放 build 下，源码中的审计文档只保存结论与复现方法。

## 10. 执行方式与结束标准

建议按以下批次开展，每批完成后再决定是否进入修改：

1. 两板获取与构建流程、配置闭环、诊断状态定义。
2. 启动边界、线程行为、资源使用与跨板契约。
3. CMake/宏整理、GUI 一致性、文档收敛。

每项发现记录：触发条件、预期与实际行为、代码位置、影响板型、最小修复建议及验证方法。区分确定缺陷、可读性改善和未来需求；不要把未测试的猜测直接列为 bug。

审计结束应得到一份按影响排序的短清单，而不是全面重写方案。修改时优先修复真实行为不一致，再改善命名和组织。除非另有明确需求，不增加运行时 MCU 抽象、设备注册中心、通用恢复状态机或多层配置框架。
