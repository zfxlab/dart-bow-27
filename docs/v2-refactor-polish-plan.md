# H7/F4 V2 架构现状评估与下一阶段修改建议

## 当前代码审查与修改结果：2026-09-11

### 结论

当前可以在 H723 MC02 与 F407 C 板之间进行构建切换，共享 `pnx_modules`、`pnx_devices`、`pnx_libs`。切换需要选择板型及匹配的 BSP 分支，并使用各自的构建目录；不是运行时切换，也不会自动替用户切换 Git 分支。本次按上下文将“F7”理解为 H7，未验证 STM32F7。

主要问题不是 BSP 缺少一层抽象，而是应用入口、诊断例程和生成配置混淆了不同层的职责。本轮修复均放在已有生产文件中，没有增加工厂、注册中心、运行时 MCU 判断或新的适配层。新增文件只有 `tests/v2-validation/validate.py`，用于复现跨板组合验证。

### 发现与处理

| 问题 | 影响 | 本次处理 |
| --- | --- | --- |
| F4 生成的 `App_ThreadX_Init` 为空，未调用 `app_start` | 镜像能链接，但上层应用及服务会被链接器裁掉，不能据此声称模块适配通过 | 在现有 `diagnose/app.cpp` 统一两个 ThreadX 入口；CMake 排除生成的 `app_threadx.c`。保留 CubeMX 外设初始化与 `tx_application_define`，不修改生成文件 |
| `board.json.devices.*.enabled` 混合固定接线与应用选择 | 同板更换机器人也需要修改板级描述 | 板级只保留固定器件绑定；BMI088/LED 启用选择移到 `robot.json`，省略即禁用消费者 |
| AHRS 的 BMI088 实现无条件编译 | F4 或 H7 只选 DMIMU 时仍依赖 BMI088 服务；诊断代码也直接调用它 | 沿用 `HAS_AHRS` / `HAS_DMIMU`，分别编译服务及诊断路径；DMIMU-only 从自己的输出订阅 |
| 任意电机列表自动启用固定三电机例程 | F4 合法的 `validation_motor` 配置引用不到 `motor1/2/3`，编译失败 | `test.motor_demo` 显式选择专用例程，默认关闭；驱动源码仍按机器人设备列表选择，H7 示例保持显式开启 |
| CMake 全局加入 BSP `src` 头文件目录 | 上层可以直接依赖 HAL 桥接与私有绑定 | 私有目录只赋予 BSP 源文件及生成的绑定源；共享消费者只拿公共目录 |
| USB/test 参数按整个组补默认值 | 只填一个字段时，其他默认常量消失，造成编译失败 | 改为逐字段保留默认值 |
| 不使用 preset 且未指定工具链时可能寻找宿主编译器 | `PNX_BOARD` 已选中仍配置失败 | 缺省采用项目 ARM 工具链，仍允许显式工具链覆盖 |

### 配置边界

| 文件 | 应当描述 | 不应承担 |
| --- | --- | --- |
| IOC 与 CubeMX 输出 | 外设实例、引脚复用、时钟、DMA、NVIC、USB/ADC/timer 配置 | 机器人设备组成与业务协议 |
| `boards/<board>/board.json` | PCB 固定接线、板载器件绑定、有效电平、DMA 可访问内存等静态事实 | 当前机器人是否启用板载器件、电机数量、协议策略、队列深度 |
| `configs/boards/<board>/params.json` | 应用接口选择、服务运行参数、诊断开关 | 重复 IOC 硬件配置或改写板载固定接线 |
| `configs/boards/<board>/robot.json` | 本机器人使用哪些器件、型号、协议地址和连接的 CAN 总线；是否使用板载 BMI088/LED | 改写板载器件固有接线 |
| `build/.../generated/` | 上述输入生成的枚举、常量与私有 HAL 绑定 | 手工维护的第二套配置 |

同一块 PCB 更换机器人时，`board.json` 应保持不变。外接接收机或传感器换接口属于应用接线选择；不能因此改变板载 BMI088 的 CS/DRDY。若板卡改版或实际固定接线变化，应修改对应板型描述并与 IOC 保持一致。

F4 的 `devices: {}` 表示当前未描述相应板载器件绑定，并不证明 PCB 缺少这些元件。不能为了让 BMI088 在 F4 上通过编译而猜测 SPI/CS/DRDY/加热引脚。本轮保持未启用状态。

生成回归已经验证：H7 关闭 BMI088/LED 后，`bsp_bindings.hpp` 内容保持一致，应用 feature 宏随机器人选择变化。固定事实和消费选择因而具有不同的生效路径。

### 共享代码适配评估

**pnx_modules**：本轮实际修复 AHRS 的隐式 BMI088 依赖。BMI088 和 DMIMU 继续共用同一个源文件，各自按配置编译，无需再拆多个服务接口。现有消息通道、回调和 ThreadX 服务结构可以保留。两板 DMIMU-only 完整镜像均保留服务入口，不再依赖 BMI088。

**pnx_devices**：本轮扫描未发现共享设备直接使用 STM32 HAL、固定 H7 UART/FDCAN 实例的情况。CAN 设备使用生成配置和共享 BSP；F4 仍限定 Classic CAN。合法 Classic 电机组合已通过驱动编译及完整镜像链接，但这不等于自动创建设备或验证电机通信。应用仍需要构造具体设备并向现有 motor service 注册。专用三电机诊断配方不是任意机器人组成的实现。

BMI088 仍是按板载固定绑定接入的设备实现，当前不支持任意数量的外接 BMI088 实例。现有需求没有证明需要把它改成通用工厂或配置注入体系。LED 也仍为 SPI LED 器件；F4 三色 GPIO LED 通过 GPIO 诊断使用，不能因为都叫 LED 就强行统一为同一种设备。

**pnx_libs**：本轮静态扫描未发现直接 STM32 HAL 或具体板载外设依赖。实际消费者随两板镜像编译。DMA 放置/缓存行为仍由 BSP 与生成的内存事实承担，不下沉进算法、消息或协议库。此结论不代表所有未被使用的库路径都做过运行测试。

**BSP 契约**：对应公共头文件在规范化换行后内容一致；H7/F4 的差异继续留在编译期选择的实现中。`bridge_usb.h` 保持在 `src` 合适，因为它是私有 USBX/PCD 桥接契约；真正需要修复的是 CMake 将其目录暴露给所有消费者的问题，本轮已处理。无需为了目录整齐把它变成公共头文件。

### 切换方式与下一步

普通使用方式是先让 `pnx_bsp` 位于对应 V2 分支，再执行 `cmake --preset h723-debug` 或 `cmake --preset f407-debug`，随后执行对应 build preset。两个 preset 使用不同目录。并行开发两板时，可以保留 H7 主工作树，用 `-DPNX_BSP_SOURCE_DIR=<F4工作树绝对路径>` 指定 F4 实现。

接下来优先完成三件事：

1. 在 F4 上观察共享应用入口、GPIO 诊断和 DMIMU 收发，确认本轮保留进镜像的服务实际运行；H7 做对应回归。
2. 根据板卡原理图补齐 F4 板载器件固定绑定，再在机器人配置中启用所需器件。当前已有外设初始化不等于已有器件逻辑绑定。
3. 新机器人在应用层直接构造需要的设备和服务。现有三电机诊断仅保留为特定示例，后续若要通用化诊断，应另行定义诊断输入，而不是把诊断配方变成共享 BSP/生成器的设备架构。

F4 USB 仍按现有配置关闭；本轮没有改变设备身份决策。Flash 仍维持延期。暂时不建议为这些未完成事项增加运行时能力框架或统一生命周期抽象。

评估日期：2026-09-09

## 1. 总体判断

V2 的架构方向已经稳定：公共 BSP 契约统一，MCU 后端在构建时选择，IOC 与 CubeMX Board 输出拥有硬件配置，生成器提供逻辑绑定，Device/Module 使用公共接口。

下一阶段应从“逐个 BSP 模块统一接口”转到“配置、生成、共享消费者和构建组合的收尾”。当前主要问题集中在生成器残留的 H7 假设、缺失绑定的默认值，以及部分文档约束尚未落实到产品构建图。

F4 当前采用精简设备组合。它可以证明已有配置能够形成完整镜像，但不能证明添加合法 CAN 设备后依然能够生成和编译。继续只重复空设备 F4 构建，无法覆盖已经发现的适配缺口。

本阶段不需要新增 BSP 虚拟接口、运行时能力框架、注册中心、恢复状态机或通用生命周期管理。优先修正已有代码中的事实来源和依赖方向。

## 4. 必要检查的范围

检查应放在最早且能够准确判断的边界，并复用现有判断。已经在生成阶段确定的板级事实，不需要在 Device、Module 和 BSP 再各检查一次。

| 条件 | 处理位置与方式 |
| --- | --- |
| 所选 BSP family 与 board 不一致 | 保留现有 configure 失败 |
| 已启用功能引用不存在的资源 | 生成阶段明确报错，优先复用现有校验 |
| 功能明确关闭 | 源选择或现有 feature guard 关闭消费者；不制造有效资源默认值 |
| 调用参数、DMA 内存、HAL 操作结果 | 保留现有 BSP 必要检查 |
| IRQ/异步借用对象的使用约束 | 公共契约说明，配合实际消费者审查 |

本轮不加入：

- 运行时重新扫描或验证整份板配置；
- 自动尝试其他 UART/CAN、自动选择第一项资源；
- 配置失败后的回滚、重试或恢复状态机；
- 为每个对象增加 generation counter、guard 或注册生命周期框架；
- 为所有 JSON 字段重新建设一套通用校验语言；
- 仅为证明简单赋值或路径整理而编写实现镜像式测试。

## 6. P0：落实 Flash deferred

### 6.1 当前问题

[H7 Flash 公共头](../pnx_bsp/flash/include/bsp_flash.hpp) 仍声明 `erase_sector`、`write_flash_word` 和固定 `flash_word_size`。[实现](../pnx_bsp/flash/src/bsp_flash.cpp) 存在直接擦除、编程路径，没有已批准的保留数据分区约束。现有 H7 编译数据库包含该 BSP 源文件。

这与 `AGENTS.md` 中 Flash deferred、不开放固件 Flash 写能力的决策不一致。本次 Device/Module/diagnose 调用扫描未发现这两个接口的消费者，但“没有消费者”和“未作为公共能力提供”是两件事。

### 6.2 建议修改

从 V2 产品源选择和公共可见入口移除未批准的 Flash 写接口。H7/F4 都应检查，不能只在父仓库排除一个源文件后，仍将可写接口保留为正常公共头。

优先采用直接删除 V2 暂不支持的公共能力，或将确有保留理由的历史实现移至明确的非产品位置。历史版本已经由 Git 保存，无需为未来可能使用而建立实验开关系统。

此次不设计分区、不统一编程粒度、不添加掉电恢复协议。CubeMX HAL 自身的 Flash 驱动不等于 V2 BSP 公共写能力，不应为排除 BSP 接口而顺带修改生成的 HAL 源。

### 6.3 验收

- V2 公共入口不再提供这两个写操作。
- 产品 BSP 源图不包含被延期的实现。
- 现有消费者无新增缺失依赖，双板受影响目标正常构建。
- `AGENTS.md` 继续写 deferred，不将本次移除记为 Flash implementation done。

## 7. P1：修复 robot CAN 资源列表

### 7.1 当前问题

IOC parser 区分两个列表：`PNX_IOC_FDCAN_HW` 保存 FDCAN，`PNX_IOC_CAN_HW` 保存通用 CAN 资源，包含 H7 FDCAN 与 F4 bxCAN。

生成器中的 DMIMU 和 motor 总线存在性检查仍引用 `PNX_IOC_FDCAN_HW`。因此 F4 即使在 robot.json 中选择真实存在的 `can1` 或 `can2`，也会被拒绝。当前 F4 motor list 为空、DMIMU 未启用，所以默认构建绕开了该路径。

### 7.2 建议修改

将共享设备的总线存在性检查改为 `PNX_IOC_CAN_HW`。帧类型、ID 范围和设备协议约束继续使用现有检查，不再新增 capability 对象或运行时后端查询。

同时整理直接相关的错误信息，将共享路径中的“FDCAN instance”改为“CAN bus”等通用表述。MCU 私有绑定中的 FDCAN 名称仍保留。

`robot.json` 的 `can_type` 表达设备所要求的帧格式，应与 IOC 发现的模式相容；生成器不能据此改写 IOC 模式。

### 7.3 验收

以独立测试输入建立一个 F4 Classic CAN 电机组合，不改默认产品 robot.json：

- `can1` 或 `can2` 的合法配置生成成功。
- F4 引用 `fdcan3` 仍在 configure/生成阶段失败。
- F4 请求 FD 仍被现有类型检查拒绝。
- 对非空 F4 设备组合做编译链接，暴露可能被零设备选择掩盖的消费者依赖。

这些是针对实际缺陷的回归用例，不需要枚举全部 CAN ID 或建立通用组合测试平台。

## 8. P1：UART none 语义与 VT03 绑定

### 8.1 当前问题

生成器找不到 DR16、VT03、PS2 UART 或 referee 的 UART 时，将其别名设为 `0`。现有 F4 生成配置中 USART1 也是端口 `0`。

因此缺失角色仍可表现为一个有效 USART1 端口，`port_enabled()` 无法区分它与真实绑定。当前 feature 关闭相关模块，限制了默认产品中的影响，但别名本身仍有歧义。

此外，VT03 的资源发现、别名和部分判断仍固定使用 `uart7`。共享模块的连接选择不应隐含要求所有板都提供 UART7。

### 8.2 建议行为

| 输入状态 | 目标行为 |
| --- | --- |
| 模块启用，绑定有效 | 生成有效别名，选择消费者 |
| 模块启用，绑定缺失或资源不满足现有要求 | 复用现有校验，在生成阶段失败 |
| 模块关闭，绑定 none | 关闭消费者，别名不得回退到端口 0 |

推荐优先不生成关闭功能专属的有效别名，并核对共享头、构造器和源文件的现有 feature guard。若某个仍参与构建的公共配置确实需要占位值，则提供单一、明确的无效端口值，并复用 BSP 的范围判断；不要引入 optional 配置容器或自动端口选择框架。

当前生成器已经对显式启用的 DR16、VT03、PS2 UART 检查部分硬件条件。本轮应修正绑定来源和关闭路径，不能再平行增加第二套同义检查。

VT03 改为读取明确的应用 UART 绑定。选择复用现有 remoter 绑定，还是增加单一 VT03 角色，应依据现有配置能否表达独立接线决定；只保留一个有效入口，H7 的 UART7 选择写入配置。

### 8.3 验收

- 当前 H7 功能选择和接线结果保持一致。
- F4 none 不再形成可误用的 USART1 角色别名。
- 启用 UART 模块但缺少有效绑定时，错误指向具体配置角色。
- 修改 VT03 绑定后，生成器不再用写死 UART7 的分支覆盖选择。

## 9. P1：移除 DMIMU 默认物理总线

### 9.1 当前问题

[dmimu.hpp](../pnx_devices/imu/dmimu/include/dmimu.hpp) 的 `transport_config` 默认使用 `bsp::can::bus::fdcan3`。F4 的生成枚举不包含该成员。即使 robot.json 提供 `can1`，头文件仍须先通过编译，因此不能只修改 JSON 解决问题。

### 9.2 建议修改

由 robot 生成配置或组合层显式构造 transport config 并传入总线，Device 公共头不选择板级外设。

修改时检查 `config transport{}` 等默认构造路径，避免仅删除字段初始化后又隐式选择总线 0。优先让需要资源的构造位置显式提供配置；若现有静态对象初始化结构需要调整，局部修改相应构造点即可。

DMIMU 的 Classic 帧要求和现有通信参数继续保留。无需增加动态总线发现、设备注册中心或配置有效性状态机。

### 9.3 验收

H7 的 fdcan3 由配置明确提供；F4 的合法 CAN 组合能编译 DMIMU 头与实现。测试不要求默认 F4 产品启用 DMIMU，也不宣称设备通信已经通过硬件验证。

## 10. P2：收敛 feature 语义

### 10.1 当前问题

`HAS_MOTORS` 当前由“IOC 有 CAN”推导，源文件选择却主要依赖 `robot_motor_count` 和各 motor protocol 开关。F4 因此出现 `HAS_MOTORS=1`、motor count 为 0 的状态。

硬件存在与产品设备存在本来就是不同维度，不应强行合并；但变量名称和消费者必须准确对应其含义。

### 10.2 建议修改

- CAN 硬件存在继续由已有 bus count 或硬件事实表达。
- 若 `HAS_MOTORS` 用于产品设备选择，则从 robot motor list 推导。
- 各协议开关继续从 motor model 集合推导，不增加第二份协议启用列表。
- 消费者逐项改用对应事实，不全仓机械替换全部 `HAS_*`。

生成顺序可能需要局部调整：先解析 robot 的必要组合信息，再输出 feature 和源选择变量。此次只调整已经证明重复或含义错误的派生规则，不重写整个生成器。

## 11. P2：CMake 的适度整理

### 11.1 当前状态

顶层使用递归扫描再过滤源文件，且从全部头文件目录收集 include path。当前能工作，但父工程需要知道较多子模块目录结构，私有头也容易被共享消费者直接 include。

同一个固件目标拥有 Board/HAL include path 不等于公共契约已经泄露 HAL；真正需要约束的是公共头和共享消费者的依赖。因此不能仅凭全局 include path 就认定架构失败。

### 11.2 建议分两步实施

第一步保留当前目标结构，输出 build-local 最终源清单，整理明确的公共和私有目录列表，复用现有源过滤函数。优先确保零资源模块、Flash deferred 和功能开关的选择可以直接检查。

第二步仅在顶层规则仍明显难维护时，为 BSP/Device/Module 增加普通 CMake target 或局部 source list。公共依赖与私有 Board/HAL 依赖通过 CMake 可见性表达。迁移时保持现有链接和编译定义语义。

本阶段不为了架构形式拆分每个目录，也不引入插件式构建系统。`PNX_BOARD` 与匹配 BSP 分支的现有流程保持不变。

### 11.3 schema 与 manifest 的取舍

目前 family 校验已经存在，私有绑定形状的大部分不匹配会在编译时暴露。schema version 可以在后续出现真实的私有协议演进需求时加入，但不应先于已确认的 CAN/UART 缺陷。

本轮不要求多重 hash、运行时 manifest 核验或每个模块独立版本协商。需要记录构建来源时，简单记录 board、BSP 路径/提交和输入位置即可。

## 12. 异步契约：先说明和核对，不批量增加机制

现有核心约束应保留：callback 非拥有、异步 buffer 生命周期有效、IRQ 回调不得阻塞、H7 cache 维护由 BSP 负责、F4 仍检查 DMA 地址范围。

USB 回调在线程执行，CAN/USART/EXTI 回调主要沿 IRQ 路径执行，应在对应 API 中分别说明，不能用一个全局“所有 callback 都在任务线程”的约定覆盖。

不把“IRQ 不得阻塞”扩写为“任何浮点处理都禁止”或“所有设备必须新增接收队列”。现有电机 handler 会直接进入反馈解析；是否改到线程，应依据最坏执行时间、栈开销、共享数据一致性和总线负载。

同样，不因 EXTI 没有 detach 就自动新增停机与析构框架。当前若使用静态生命周期对象，先明确这一约束；只有出现真实动态注销消费者时再调整接口。

## 13. 需要纠正的原审查表述

| 原报告中的方向或表述 | 建议修正 |
| --- | --- |
| PWM/failsafe 缺少资源拒绝策略属于待补功能 | 已有相关生成期检查，转为针对性回归验证 |
| robot bus/type/ID 校验全部待补 | 已有检查，但共享设备的资源集合选错，先修正这个缺陷 |
| F4 未选择 SPI/PWM/ADC 后，调用应返回 not_configured | 后端未链接时不提供调用保证；应在配置/源图排除消费者 |
| Device 使用 heater/BMI088 角色会引入 BSP 设备依赖 | Device 使用逻辑角色合理；BSP 不应按设备语义硬编码实现 |
| CAN IRQ 回调只能复制入队，不能浮点解码 | 保留不阻塞要求；处理位置依实际时延与并发证据决定 |
| 共享 CAN 消费者只能使用 Classic | 跨 H7/F4 的同一配置需满足共同能力；共享代码仍可支持配置明确选择的 H7 FD |
| family 校验能阻止所有旧 build 状态 | family 只检查目标族匹配；继续使用独立构建目录，不夸大其保证 |

无需把两份已有文档再扩写成同样的大型清单。`AGENTS.md` 保存当前决策与验证状态，原审查报告区分已确认问题与一般建议，本文保存下一阶段的具体修改方案。

## 14. 分批实施与验收

### 第一批：落实已批准范围

移除 V2 Flash 公共写能力及产品源选择，核对 H7/F4 暴露面。构建受影响目标，确认当前消费者不依赖它。保持 Flash deferred。

### 第二批：修复共享组合

修正 robot CAN 列表、UART none/VT03 来源和 DMIMU 默认总线。每项先完成局部修改和相关验证，再组合运行双板构建。

最小验证矩阵：

| 配置或检查 | 目的 |
| --- | --- |
| 当前 H7 Debug / Release | 保持已有完整配置可生成、编译、链接 |
| 当前 F4 Debug / Release | 保持零资源后端选择和精简配置 |
| 独立 F4 Classic CAN motor 组合 | 覆盖默认空列表绕开的生成与消费者路径 |
| 独立 F4 DMIMU 组合 | 覆盖公共头硬编码及生成配置构造 |
| F4 引用 fdcan3 / 请求 FD | 验证修正后的通用列表没有放宽现有必要约束 |
| UART none 与显式启用缺失角色 | 验证没有有效端口回退，诊断明确 |

组合输入和输出放在独立验证位置，不覆盖默认 robot.json，也不手改 generated config。不增加产品 image selector 来承载测试组合。

### 第三批：整理和记录

收敛 `HAS_MOTORS` 等已确认的派生语义，输出源清单，视需要整理 CMake 可见性，更新原审查和 `AGENTS.md`。结构改动只运行受影响检查，不因文档排版或变量注释反复全量构建。

## 15. 硬件验证与阶段完成标准

完成上述修改后，可以声称“已验证配置的生成与共享组合构建完成”，仍不能声称双板运行行为全部验证。

后续硬件验证优先选择当前真实存在的 CAN、USART 和 H7 DMA/设备链路，检查收发、回调执行及长时间数据连续性。F4 无需为本轮验证补造 SPI/PWM/ADC；USB 身份和枚举继续按原计划独立推进。

本阶段完成应满足：

1. Flash 的公共暴露与 deferred 决策一致。
2. F4 合法 CAN 设备组合不再因 FDCAN 专用列表失败。
3. 缺失 UART 角色不再隐式选择 USART1。
4. 共享 DMIMU 头不再依赖 H7 专有枚举成员。
5. 默认双板及必要非空设备组合有明确的生成/构建结果。
6. feature、源选择和文档表达同一组产品事实。

这些收尾工作完成后，再根据具体产品需求扩展 F4 硬件资源或推进持久化能力。当前没有必要进一步扩大公共 BSP 架构。
